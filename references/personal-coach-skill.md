# 把方法保存成个人写作训练 Skill

## 目录

- 它是什么、什么时候生成
- 用户怎样选择方法
- 技能包的目录和文件格式
- 学习、陪写、批改三种模式
- 保存、安装与生成后检查

## 它是什么

把它做成一位基于这本书或这篇长文的个人写作教练。保存用户真正想练的写作动作、什么时候适合用、什么时候别用，以及对应的原文卡片。

避免承诺复制作者的个人风格。一次稿件建议练 1–2 个动作，给用户自己的声音留下空间。

## 什么时候生成

先交付完整拆书文档，再邀请用户选择。满足下面三条才生成：

1. 章节表或文本地图、原文卡片、主要写法和文风已经完成；
2. 用户已经看到方法清单；
3. 用户明确确认要保存的 3–6 个方法。

用户说“帮我选”时，推荐 3–6 个并说明推荐理由，等用户确认一次。不要替用户跳过确认。

## 怎么邀请用户选择

在文档末尾和交付消息里给一份短清单：

| 编号 | 写作动作 | 来自哪些卡 | 为什么适合当前目标 |
|---|---|---|---|
| 方法 M01 | …… | 拆句卡 C03、拆句卡 C11 | …… |

控制在 4–6 项。请用户回复编号，例如：

> 如果你想把这些方法保存成个人写作训练 Skill，请选至少 3 个、最多 6 个编号，也可以回复“全部”。我会把它做成可在不同 Agent 中使用的技能包。

飞书支持文档锚点时，把卡片编号链接到对应卡片，方便用户回看原文。

## 选哪些方法

每个方法都要符合下面四条：

- 名字是一个能直接照做的动作；
- 能指回至少一张原文卡片；
- 与用户当前写作目标直接相关；
- 能写清什么时候适合用、什么时候别用。

优先选择有两个不同章节或文本单元支持的方法。只有一个位置支持时，标成“局部写法”，避免把一次选择说成作者的固定习惯。

## 生成什么

目录名使用小写英文字母、数字和连字符，控制在 64 个字符以内。优先使用：

```text
<book-short-slug>-<goal-slug>-writing-coach
```

书名很难转成简短英文时，使用 `personal-writing-coach-01` 这类中性名称，并在正文写清书名。

生成一个主文件和四个参考文件，不加 README：

```text
<skill-name>/
├── SKILL.md
└── references/
    ├── methods.md
    ├── evidence.md
    ├── exercises.md
    └── rubric.md
```

### SKILL.md

`SKILL.md` 开头的 YAML 信息区只写 `name` 和 `description`。`description` 要包含来源文本、写作目标以及学习、陪写、批改三个使用场景。

正文保持简短，写清下面的运行顺序：

```markdown
---
name: <skill-name>
description: Coach writing for <goal> with user-selected methods distilled from <book>. Use for learning a method, planning and drafting with it, or reviewing the user's own writing with evidence-linked feedback.
---

# <书名> × <写作目标>个人写作教练

先读 `references/methods.md`。需要查看出处时读 `references/evidence.md`；出练习时读 `references/exercises.md`；批改时读 `references/rubric.md`。

## 开始

判断用户要学习、陪写还是批改。意图不清楚时，一句话问清。

## 学习

让用户选一个方法。用一张卡片说明它怎样起作用，再请用户指出自己看见了什么。

## 陪写

先问写作任务和读者。让用户选 1–2 个方法并说一句选择理由；拿不准时给两个建议。先请用户写一版，用户明确要求示范时再代写一小段。

## 批改

先指出一处已经用对的地方，再挑一处提升最大的地方。每个判断标明方法编号，必要时指回卡片编号。只示范改一句，然后给下一步动作。

## 规则

- 一次集中练 1–2 个方法；
- 保留用户自己的观点、材料和声音；
- 每个判断都能指回方法或证据卡；
- 直接说文字做了什么；
- 避免承诺复刻作者风格。
```

### methods.md

开头先写一段“这些方法合在一起是什么风格”，用 3–5 句话说明作者怎样处理观点、材料、人物、场景和句段节奏。每句话都要能指向后面的一个或多个方法，避免使用“高级、克制、深刻”这类空形容词。

然后让每个方法使用固定格式：

```markdown
## 方法 M01｜动作式名称

- 它解决什么：……
- 怎么做：第一步 → 第二步 → 第三步
- 适合：……
- 什么时候别用：……
- 用到当前目标：……
- 证据：拆句卡 C03、拆句卡 C11
```

### evidence.md

先记录书名、作者、版本或译者、这次的写作目标和生成日期。再按方法整理证据，保留最短够用的信息：

```markdown
## 方法 M01

| 卡片 | 章节位置 | 短引或准确转述 | 它证明了什么 |
|---|---|---|---|
| 拆句卡 C03 | 第 X 章 | …… | …… |
```

不要复制整张卡。短引继续遵守主 Skill 的引用长度和总量要求。

### exercises.md

每个方法配一道 8–15 分钟的小练习。给够素材、限制条件和 3 条自查项。练习要求用户做判断，避免只做同义改写。

### rubric.md

沿用主 Skill 的四步反馈：

1. 指出一处已经用对的地方；
2. 只挑一处提升最大的地方；
3. 只改一句作示范；
4. 回到相关拆句卡，看作者在类似位置怎样处理。

再加入当前写作目标的检查项，控制在 3–5 项。

## 生成后的交付流程

Skill 文件写完并通过结构检查后，继续完成下面五步。不要把“生成了一个文件夹”当成交付终点。

### 第一步：问保存还是安装

只问一个短问题：

> 个人写作 Skill 已经生成。你想保存在当前目录，还是直接安装到当前 Agent？

- 用户选“保存在当前目录”：保留在 `generated-skills/<skill-name>/`，给出可点击的完整路径，随后跳到第四步做结构验证。
- 用户选“直接安装”：先识别当前 Agent，再执行第二、三步。
- 用户没有指定保存位置：使用当前工作目录下的 `generated-skills/<skill-name>/` 作为生成源目录。

GitHub 仅用于用户明确提出的分享、备份或版本管理。本地使用无需创建仓库、提交或推送。

### 第二步：识别当前 Agent 的安装位置

优先读取当前客户端提供的环境信息、Skills 列表或官方本地配置，不靠猜测。常见默认位置如下：

| 当前 Agent | 本地 Skills 位置 | 安装方式 |
|---|---|---|
| Codex | `~/.agents/skills/` | 软链接优先，复制为备选 |
| Claude Code | `~/.claude/skills/` | 软链接优先，复制为备选 |
| Kimi Code | `$KIMI_CODE_HOME/skills/`；未设置时优先使用 `~/.agents/skills/`，也可使用 `~/.kimi-code/skills/` | 软链接优先，复制为备选 |
| WorkBuddy | 客户端“添加技能 / 上传技能”入口 | 在本地生成 ZIP，提示用户导入 |
| 其他 Agent | 当前客户端公开的用户级或项目级 Skills 目录 | 找不到时只问一次具体目录 |

当前 Agent 明确公开了其他路径时，以当前环境为准。不要因为仓库 README 里出现某个目录就覆盖客户端现场信息。

上面的五个文件构成跨 Agent 使用的核心技能包。`agents/openai.yaml` 只在当前 OpenAI 客户端明确需要展示信息时按需生成，不计入核心文件，也不要求其他 Agent 读取。

### 第三步：安全安装

1. 先解析生成源目录和目标目录的完整路径。
2. 检查目标是否已经存在。不存在时再创建父目录并安装。
3. 同一台机器上优先创建软链接，让后续修改继续生效；环境不支持软链接时复制整个文件夹。
4. 目标已有同名 Skill 时，先比较来源与目标。它们指向同一目录就直接报告已安装；内容不同就告诉用户差异并询问覆盖、换名还是取消。
5. 不静默覆盖、删除或合并用户已有文件。
6. WorkBuddy 等需要上传的客户端，把整个 Skill 文件夹压成 ZIP，保证 `SKILL.md` 位于压缩包内第一层 Skill 目录中；生成后给出本地 ZIP 路径和导入入口。

### 第四步：验证能否识别

验证分两层，并分别报告结果：

**文件验证**

- 安装目标存在，目录名与 YAML 信息区的 `name` 一致；
- `SKILL.md` 存在，开头的 YAML 信息区只有 `name` 和 `description`；
- `references/methods.md`、`evidence.md`、`exercises.md`、`rubric.md` 都存在；
- `SKILL.md` 中引用的相对路径都能找到；
- 当前环境有 Skill 校验器时运行它，并修复错误后再继续。

**客户端识别验证**

- 当前 Agent 提供 Skills 列表、重扫或识别检查时，执行检查并确认 `<skill-name>` 出现在列表中。
- 当前客户端只在启动或新会话时扫描 Skills 时，明确报告“文件安装已通过，客户端识别需要重开会话”，随后给一条识别测试指令。
- WorkBuddy 需要用户完成界面导入时，先报告 ZIP 已就绪；用户导入并启用后再验证。
- 没有看到 Skill 名称或触发证据时，不宣称“识别成功”。

识别测试指令：

```text
请列出并使用 $<skill-name>，告诉我它提供哪三种写作模式。
```

不支持 `$skill-name` 调用语法的 Agent，改成“请使用 <skill-name>”。

### 第五步：给三条首次使用指令

把 `<skill-name>`、写作目标和方法编号替换成真实内容，交付三条完整指令。三条分别覆盖学习、陪写、批改：

```text
使用 $<skill-name> 教我方法 M01。先用一张拆句卡说明它怎样起作用，再给我一道十分钟练习。
```

```text
使用 $<skill-name> 陪我写一篇<写作目标>。我会提供采访笔记，请先帮我选择一到两个方法，再带我完成第一版。
```

```text
使用 $<skill-name> 批改下面这篇<写作目标>。请先指出一处已经有效的写法，再挑一处提升最大的地方，只示范修改一小段。
```

不支持 `$skill-name` 的 Agent 去掉 `$`。三条指令必须带入真实 Skill 名，不能保留尖括号占位符。

## 生成后检查

- 用户是否亲自确认了 3–6 个方法；
- 四个引用文件是否都存在；
- `SKILL.md` 的相对路径是否都能找到；
- 每个方法是否有卡片依据；
- 每个方法是否写了什么时候适合用、什么时候别用；
- 三种模式是否都要求用户参与判断或写作；
- 全部方法是否仍然服务于同一个写作目标；
- 是否避免了作者风格复刻承诺；
- 是否扫描了先否定一种说法、再转向另一结论的对比句式。
- 是否已经询问“保存在当前目录还是直接安装”；
- 选择安装时，是否根据当前 Agent 使用了正确目录；
- 是否保护了已有同名目录，没有静默覆盖；
- 是否分别报告文件验证和客户端识别结果；
- 是否给出学习、陪写、批改三条可直接复制的真实指令。
